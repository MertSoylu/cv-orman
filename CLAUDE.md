# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## This is NOT the Next.js / React you know

This repo runs **Next.js 16 (Turbopack) + React 19** — recent enough that APIs, conventions, and file structure may differ from training data. Before writing Next-specific code (route segment config, caching/`revalidate`, server vs client component rules, `app/` conventions), read the relevant guide in `node_modules/next/dist/docs/` and heed deprecation notices rather than assuming older-Next behavior.

## What this is

`cv-orman` is a standalone Next.js page (deployed to a subdomain of mertsoylu.dev) that renders the owner's own GitHub repos as trees in a 3D forest. Tree size comes from stars/commits/age, tree color/wilt comes from days-since-last-push, tree species comes from primary language. It's a single-user, single-page app — no auth, no multi-tenancy, no database.

## Commands

```bash
npm run dev      # Turbopack dev server, http://localhost:3000
npm run build    # production build (also runs the TypeScript check)
npm run start    # serve the production build
npm run lint     # eslint (flat config: eslint-config-next core-web-vitals + typescript)
npx tsc --noEmit # typecheck only, faster than a full build
```

There is no test runner configured in this repo. Verification is tsc + lint + build, plus manually checking `/` in a browser (this is a visual/3D app — type-checking does not catch rendering or hydration bugs).

Required env vars (see `.env.example`): `GITHUB_TOKEN` (a GitHub PAT with `public_repo` scope — despite the `.env.example` comment, a fine-grained `github_pat_...` token has been confirmed to work fine against the GraphQL endpoint, not just classic tokens) and `GITHUB_USERNAME`. Without both, `/` and `/api/repos` return a 502 with an explanatory message instead of failing silently.

## Architecture

### Data pipeline (no database, stateless)

Growth/health are recomputed from live GitHub data on every fetch, cached only via Next's ISR (`revalidate`) — there is deliberately no DB, because GitHub's API already exposes everything needed to derive current state.

```
lib/github/query.ts        GraphQL query string (single query, paginated via `after`)
  -> lib/github/client.ts  fetchAllRepoNodes(): pages through all repos, throws GitHubFetchError
  -> lib/github/normalize.ts  normalizeRepoNodes(): drops archived repos (no GraphQL arg for that —
                               isFork is filtered server-side, isArchived must be filtered here),
                               delegates scoring to lib/forest/growth.ts (computeGrowthScore),
                               lib/forest/health.ts (computeHealthStage), and lib/forest/species.ts
                               (mapLanguageToSpecies, a plain language->species lookup table)
  -> lib/forest/path.ts    the winding trail centerline, as pure math (no three.js)
  -> lib/forest/layout.ts  computeForestLayout(): walks that centerline -> {x, y} per tree id
  -> PlacedTreeData[]      passed straight into the renderer
```

`src/lib/forest/treeData.ts` (`TreeData` / `PlacedTreeData`) is the contract between the data layer and the renderer. Renderers only ever read the precomputed `growthScore` (0-1, drives scale) and `healthStage` (0-1, drives color/wilt) — never raw `stars`/`commitCount`/`lastPushedAt` directly. Keep that separation: it's what let three renderer prototypes (2D SVG, 3D, 2.5D parallax) get built and compared against the same data before 3D was picked and the other two deleted.

`app/page.tsx` is a Server Component that calls `fetchAllRepoNodes` → `normalizeRepoNodes` → `computeForestLayout` **directly**, not by fetching its own `/api/repos` route, then hands the resulting `PlacedTreeData[]` (plus any fetch error) to `components/ForestPageClient.tsx` — a Client Component that owns the hero/legend overlay, stats, error/empty states, tree-selection state, and mounts `Forest3D` + `TreeDetailPanel`. `/api/repos` still exists as a standalone JSON endpoint but is not on the real page's request path. Both `route.ts` and `page.tsx` declare `export const revalidate = 3600` as a hardcoded literal — Next.js requires route segment config to be statically analyzable, so it can't just import `REVALIDATE_SECONDS` from `lib/config.ts`; keep these three in sync by hand if you change the cache duration.

`ForestPageClient.tsx` also renders a visually-hidden (`.sr-only`) `RepoFallbackList` alongside the canvas — the 3D scene has no DOM equivalent, so this is the only path screen readers, crawlers, and no-JS/no-WebGL clients have to the repo data. `Forest3D` is wrapped in an `ErrorBoundary` (class component; function components can't catch render errors) whose fallback re-renders `RepoFallbackList` visibly with a short explanatory heading — for when WebGL context creation itself throws. A `sceneReady` flag (flipped by `Forest3D`'s `onReady` prop, fired from the `Canvas`'s existing `onCreated`) gates a `SceneLoadingIndicator` overlay so there's no blank gap between the route's `loading.tsx` (server fetch) and the scene's first WebGL frame (client init) — `loading.tsx` renders the same `SceneLoadingIndicator` component so the two waits read as one continuous state.

`lib/config.ts` centralizes the tunable weights: `GROWTH` (stars/commits/age weighting + soft caps), `HEALTH` (healthy/wilted day thresholds + wilted floor), `LAYOUT` (station spacing, the two lateral bays, and the serpentine curve's amplitudes and wavelengths). What actually sets the curve constants is the **maximum slope** they imply, `A * 2pi / L` summed over both waves — the angle the walk can swing off the forward axis. Keep it under ~0.4 (22°): past that you can see one station ahead before the trail leaves the frame, the avenue stops reading as an avenue, and the gate at the trail head falls outside the frustum. `GITHUB_USERNAME`/`GITHUB_TOKEN` are read via lazy getters (`getGithubUsername()`/`getGithubToken()`), not top-level constants — `next build` imports route modules to collect segment config without ever calling the handlers, so an eager `requireEnv()` at module scope breaks the build whenever secrets aren't present at build time.

`lib/forest/path.ts` defines the exhibit's winding trail as **pure math with no three.js dependency**, so it can run on the server. The centerline is `x = f(s)` — two out-of-phase sines of forward distance — which makes tangent and normal closed-form and makes "nearest point on the trail" a cheap 1-D search rather than a spline projection. Both the data layer and the renderer consume it: `computeForestLayout()` walks it to place trees, and the renderer walks the same curve to lay the gravel ribbon, flatten the terrain corridor, place plaques and lanterns, and aim the camera. If those two ever disagree, the trail and the trees come apart, so there is exactly one definition.

`computeForestLayout()` places trees two per **station** along that curve, one to each side, offset sideways **along the curve's own normal** (so the two files bend with the trail rather than staying parallel to a fixed axis). It carries **no positional noise at all**, and that is deliberate: an earlier version jittered both offsets so pairs would not line up like fence posts, which is the right instinct for a wild wood and the wrong one for an exhibit. A botanical garden plants its specimen avenue on a grid, and the regularity is what tells a visitor the planting was chosen. Both trees of a station therefore stand exactly opposite each other at exactly the same setback; all the variation the eye needs comes from species, canopy and size. The one concession is the **bay** — a specimen above `PATH_BAY_THRESHOLD` steps one discrete bay further back so its canopy clears the walk; a discrete step keeps the files reading as lines where the continuous growthScore-scaled offset it replaced did not. There is no `PLANE_WIDTH`/`PLANE_HEIGHT` bound; the trail is exactly as long as it needs to be for however many repos exist, and the renderer derives terrain, camera and fog sizing from the actual tree spread.

### Renderer: `components/renderers/three-3d/`

react-three-fiber + drei. This is the only renderer — 2D SVG and 2.5D parallax prototypes existed during the style-comparison phase and were deleted once 3D was chosen; don't resurrect them from git history without checking with the user first.

The scene is a wooded valley with a winding gravel walk through it and a stream crossed by a plank bridge at the midpoint. It reads as an **arboretum, not a wood** — the walk is kerbed in dressed stone, gated at both ends, and each specimen stands in a pale plot squared to the path — and the whole design tension is between that discipline and the wild valley it sits in. When adding to the scene, ask which side a thing belongs on: the exhibit's furniture is aligned, edged and repeating; the valley's is seeded and irregular. Everything in it is generated in code: there are no model files and **no texture files** — bark, ground, water ripples, grass and leaf silhouettes are all synthesized at runtime by `textures.ts`.

**The one architectural idea worth understanding first**: every animated property of a tree is a *per-tree scalar*, written into a tiny `treeCount x 1` float texture (`trees/treeState.ts`) once per frame and read back in the vertex shader. Instance matrices are static. The CPU's entire per-frame cost for the forest is four floats per tree; hover, sprout-in, wind sway and the foliage LOD crossfade all happen on the GPU. The previous renderer recomposed a `Matrix4` per instance per frame, and that was its ceiling.

- `Forest3D.tsx` — scene root, and the only file `ForestPageClient` knows about (its props are unchanged: `trees`/`onSelect`/`selectedId`/`isDark`/`onReady`). Derives everything from the tree set: terrain size, fog range, shadow volume, camera framing, water extent. The default framing is deliberately **not** a fit-everything wide shot — it stands the camera square in front of the near gate looking down the walk through it, close enough that the near trees render full leaf-card foliage; surveying the whole valley is a zoom away, by which point the LOD system has already swapped distant canopies for hulls. Two things about that framing are load-bearing and easy to undo by accident. The look-at is a **distance-weighted mean** of the trail beyond the gate, not a point on it — a single distant station swings the walk hard to one side of frame as soon as the trail bends. And the eye is then backed off from the gate **along that same line**, which makes eye, gate and look-at colinear so the gate lands dead centre; backing off along the trail's own tangent instead is the obvious version and puts the gate off by however much the curve turns over the aim window. Owns `hoveredIdRef`/`selectedIdRef` (refs, not state — read every frame, never need a re-render), shared by the tree field, the plaques and the ground halo, and the `stations` memo — the trail's frame at each specimen, derived once so the plot, its edging, its stepping stones, its lantern and its plaque are all square to the same walk instead of each solving for its own.
- `imperative.ts` — **read this before writing any per-frame code.** React's compiler rules forbid property writes on values created during render, and in development the compiler's runtime *recursively freezes* the plain objects a `useMemo` returns. A uniform written as the literal `{ value: 0 }` is therefore frozen, and `uniform.value = t` becomes a silent no-op — no error, the scene just stops animating. Every uniform in this renderer is a `THREE.Uniform` (a class instance, which the freeze skips) and every numeric write goes through `setUniform`/`setOpacity`/`setEmissiveIntensity`. Three.js *methods* (`Color.copy`, `Vector2.setX`, `Matrix4.compose`) are invisible to both the freeze and the lint rule, which is why most of the animation code reads naturally; prefer them where they exist.
- Custom-shader materials (`Water`, the sky dome, `Motes`) are constructed with `new THREE.ShaderMaterial({...})` in a `useMemo` and attached via `material={...}`, **not** written as `<shaderMaterial uniforms={...}>`. Handing uniforms to the reconciler does not guarantee the material ends up holding *that* object, and a material holding a detached copy animates for zero frames while reporting nothing.
- `textures.ts` — the entire texture set, generated from a seeded, wrapping value-noise lattice (bark, ground, water normals) or drawn with canvas2d paths (leaf-cluster atlas, grass tufts), cached at module scope and built lazily on first use. Two rules: the leaf and grass images must stay **near-white**, because the species' foliage color arrives as an instance color and *multiplies* them — anything darker compounds into black canopies; and nothing here may be called during SSR (`document`, `DataTexture`).
- `trees/species/builder.ts` — one parametric recipe builds all eight species: a trunk limb, a recursive branch system, leaf cards scattered at the tips, and a coarse hull for the far LOD. `growLimb`'s `tropism` term pulls each step back toward the limb's starting direction; without it the wobble is an unbounded random walk and trunks routinely end up leaning 45°. The triangle budget lives here: twigs past the first branch level get a triangular cross-section and one ring per spine point, because there are ten times as many twigs as branches. `canopyHullGeometry` clusters leaf anchors **spatially** — slicing the anchor array by index looks equivalent and is not, since anchors are emitted limb by limb, so every blob ends up with the radius of the whole crown.
- `trees/species/presets.ts` — the eight species as pure parameter sets. Every species must stay distinguishable **by silhouette alone**; the knobs that carry that are trunk taper, branch angle, droop, and whorled vs spiral branching. `branchStart` is set high on the broadleaves on purpose: canopies that begin low bury the plaques and make the wood unwalkable.
- `trees/treeShader.ts` — the shader injection that makes bark, leaf cards and canopy hull animate off the same state texel, so they can never drift apart. Also builds the matching `customDepthMaterial` for each: without it, leaf cards cast rectangular shadows and shadows slide off swaying trees.
- `trees/TreeField.tsx` — buckets every tree by `(species, variant)` and draws three InstancedMeshes per bucket. Foliage LOD is a **shader-side crossfade**: whichever representation isn't wanted collapses to zero size (degenerate triangles cost no fill), so there is no CPU restructuring and no pop. All pointer events go through `TreeHitProxies` — one invisible eight-sided cone per repo tree, written with `colorWrite: false` rather than `visible: false` so it is unambiguously present for the raycaster. Leaving raycast enabled on the real foliage would test millions of triangles per mouse move, so the real meshes get `raycast = () => {}`.
- `trees/decor.ts` — unlabelled filler trees. A personal repo list is a dozen entries and reads as "some trees on a hill", not a forest. These are appended to the *same* instancing buckets, so a hundred of them cost a hundred instances and zero draw calls, and they only use species already present in the repo set. They carry no data and take no clicks. Because they are drawn from the same species and the same builder as the exhibit's own trees, they are held back on every axis they could compete on: they stand outside a 10-unit band along the trail (wide enough to leave a clearing behind the specimens, narrow enough that the wood still stands close behind them — pushed further out it reads as a bald lawn with a wood somewhere beyond it, and the specimens have nothing to be silhouetted against), they are capped below `growthToScale`'s SCALE_MIN (so *every* repo tree outgrows them), and they are rejected inside a cleared radius around each repo tree. Trail distance alone does not do that last one — the trail winds, so a point well clear of the centerline can still land directly behind a repo tree a bend away.
- `terrain/heightfield.ts` — the ground as a pure function. The terrain mesh, every tree, every fern, the trail, the plaques and the camera's floor clamp all sample this; the moment two systems disagree about where the ground is, props float and trees sink. Note that the stream carves a **floodplain** before it carves its bed — a fixed-depth channel cut into rolling hills buries the water surface under the high ground. The channel's half-width is a function of world X (`streamHalfWidth`), not a constant: slack pools alternate with tight runs, and a gaussian pinch at the trail crossing gives the bridge a narrows to span. `streamFlow` falls straight out of that width and drives the water shader. The bed profile is **parabolic in `q = distance / halfWidth`**, which is what puts the waterline at a constant *fraction* of the local half-width (~0.72) everywhere — `props/Waterside.tsx` places against that one number instead of solving for the surface itself. `pathDistance` goes through a precomputed table rather than `lib/forest/path.ts`'s exact `nearestOnPath`, because building a terrain mesh queries it once per vertex.
- `terrain/Terrain.tsx` — one displaced grid, vertex-colored by what the ground *is* (rough turf / mown verge / worn edge / riverbank / exposed rock) with a single shared grain texture multiplied over the top. One material, one draw call, no splat map to author. The **mown band** flanking the walk is the ground plane's whole contribution to the exhibit reading, and it replaced a wide band of worn dirt that said the exact opposite: a path spreading into mud is what happens where nobody maintains anything. What is left of that dirt is a thin line right at the gravel's edge — it has to stop *inside* the kerb, because a verge spilling past the stone is how the crossing ended up with a bald apron around it, with a wide verge, a wide wet margin and the bridge gap all landing on the same few metres.
- `terrain/Kerb.tsx` — dressed stone blocks laid end to end down both sides of the gravel, each seated on the terrain and squared to the local tangent, split at the stream exactly as the ribbon is. Cheapest and loudest signal in the scene that the walk was *made* rather than worn, because the eye settles that question at the ground plane before it ever looks up. Blocks stay slim and low: the kerb's job is to draw a *line*, and a block heavy enough to read as an object in its own right stops drawing one. `KERB_CLEARANCE` is exported because the kerb is the walk's visible edge, so it is what the rest of the exhibit sets out from — plaques stand just clear of it, specimens' stepping stones start at it.
- `terrain/Trail.tsx` — the gravel ribbon, dropped onto the terrain and **split** where the stream crosses; the bridge spans the gap, and `Kerb` edges it. `trailHalfWidth(s)` lives in `crossing.ts` rather than here because the ribbon is no longer the only thing that needs it — a kerb built off a constant half-width crosses onto the gravel wherever the ribbon happens to be at its widest. Its deck sits level with the two bank lips, not with the terrain at the gap's midpoint — the midpoint is the bottom of the channel, and a deck placed there reads as a ramp sinking into the water. The bridge is the one built object in the scene, so it carries all the scene's evidence of a human hand: individual cambered boards rather than one box (at trail level the eye reads the board joints first), stringers, rails and posts all sampling the same `archAt` parabola so the structure cambers as one object, and four piles reaching below the water surface. Five instanced meshes, all static.
- `terrain/crossing.ts` — the one place the trail meets the water: where the gravel stops, where the deck starts, and the parabola (`archAt`) every part of the bridge cambers along. The span is measured against the **waterline**, not the channel — the channel is ~1.4x wider than the water in it, and measuring the wrong one is how the deck ended up two and a half times the width of the creek it crossed. `heightfield.ts` bends the channel square to the trail here (`STEER_SLOPE`) and pinches it to a narrows: an oblique crossing is the single thing that makes a footbridge look wrong, because the deck has to be longer than the water is wide just to reach the far bank.
- `terrain/Water.tsx` — reflects the *sky only*, evaluated analytically from the reflected view vector using the same colors the sky dome is using this frame. Real planar reflection would mean a second full scene pass. The sky mix is capped well short of a mirror on purpose: a faithful fresnel takes it to ~1 at the grazing angles the trail-level camera sees the stream from, and this scene's daytime horizon is a warm sand color — so a physically-correct surface renders as an exact color match for the riverbank beside it.
- `atmosphere/Atmosphere.tsx` — sky dome, fog, the three scene lights, and a visible sun and moon. The theme toggle is an **animation, not a swap**: one eased `dayFactor` drives every value each frame, so flipping dark mode plays a sunset. Every JSX prop here is a mount-time seed that the frame loop overwrites — moving any of them back onto React props is what makes the transition snap. The star field is a hash in the sky fragment shader, not geometry. Night is lit deliberately brighter than intuition suggests; a weak key light collapses foliage to silhouette. The sun sits **low** — late afternoon, not midday. Overhead light flattens a forest: canopies light uniformly, shadows pool underneath, and the walk reads as an evenly-lit strip. At a raking angle each specimen lays a bar of shadow *across* the gravel, and since the stations are evenly spaced those bars come out evenly spaced too — the cheapest rhythm in the scene, and the one that most makes the walk read as a walk. Raising `sunElevation` back toward the zenith throws all of that away.
- `atmosphere/skyState.ts` — live sky colors shared **by reference** between `Atmosphere` (writes) and `Water` (reads). Routing a continuous per-frame color through React state would re-render the scene graph sixty times a second to communicate two colors.
- `atmosphere/GroundFog.tsx`, `atmosphere/Motes.tsx` — drifting mist layers, and fireflies by night / pollen by day. Mist opacities are low by design: these planes are the width of the valley, so anything above ~0.15 stops reading as mist and becomes an opaque sheet. Mote drift is entirely in the vertex shader; `uMotion` drops to zero under reduced motion rather than the frame callback being skipped, which would freeze them mid-drift instead of settling them.
- `props/Undergrowth.tsx` — rough grass, a short **mown fringe**, shrubs, rocks, fallen logs and the trail lanterns, all instanced (six draw calls for the whole ground cover) and all placed by rejection sampling against `sampleTerrain` plus `insidePlot`, so nothing grows in the water, on the gravel, off a cliff, or inside a specimen's bed. The mown fringe is the same tufts cut short, filling the band between the kerb and the rough grass: leaving that band as bare vertex colour was cheaper and read as a bald strip, because next to real three-dimensional tufts a flat-shaded band looks like missing geometry rather than short grass. It is the one field that skips the terrain-richness thinning (`evenCover`) — mown ground is uniform by definition. Grass sway reads its phase out of `instanceMatrix` in the vertex shader, so the field needs no per-instance data upload at all. Lantern globes are emissive, not real lights — a dozen shadow-casting point lights would cost more than the rest of the scene, and bloom sells the glow just as well.
- `props/Gateway.tsx` — the threshold at each end of the walk: a pair of stone piers with bronze caps and a beacon on each, over a sill of slabs laid across the gravel. A trail that begins somewhere in the grass and ends somewhere in the fog has no first or last moment, and an exhibit is nothing but a sequence of moments in a chosen order. Both gates are one set of four InstancedMeshes; both piers of a gate share the centerline's height rather than each sampling the ground under itself, because a built structure has one datum and a gate whose halves sit at different heights reads as broken rather than as following the land. `PIER_HEIGHT` is set against the **page**, not the scene: the legend card takes the bottom band of the canvas, so a gate the height of a person is one whose base is behind a card.
- `props/Waterside.tsx` — reeds in the shallows, rolled stones on the margin, lily pads on the slack pools, and a mist strip lying along the channel. Everything here is placed against the *channel* rather than against the terrain — offsets are fractions of `streamHalfWidth`, so the whole margin widens with the pools and pinches into the narrows for free. The mist follows the stream rather than the valley, because a plane wide enough to cover the terrain puts river mist over the hilltops.
- `props/TreeMarkers.tsx` — the plot, edging, stepping stones and lantern that mark a tree as an exhibit specimen. This is what makes a repo tree findable once you step off the trail, where the plaque is no longer legible. Two decisions carry it. The plot is a **superellipse squared to the walk**, not a wobbled circle: a clearing shaped by weather is what a circle looks like, and a rectangle aligned to the path is what a gardener looks like, and the exhibit turns on the difference — because each plot takes its angle from the trail's own tangent, the plots down one side stay parallel to each other however far the trail winds. And the bed is **pale raked gravel**, not the dark earth it started as: dark earth under a canopy sits at almost exactly the luminance of turf in shade, so the plots were invisible past a few paces and the specimens went back to looking like any other tree. The lantern is emissive with a **higher day floor** than the trail lanterns, because it is wayfinding rather than atmosphere, and it sits at a fixed plot corner rather than being resolved per tree, so the two specimens of a station carry mirrored lanterns and the walk gets a regular file of lights. Plots are one conformed geometry, not instanced quads: a flat plane on sloping ground either floats or has the hill cut a bite out of it, and there are only ever a handful of repo trees, so conforming still costs one draw call. `insidePlot` is exported for `Undergrowth` to reject against — testing the real superellipse rather than a bounding circle matters, since the plots are up to three times longer than they are wide.
- `props/wind.ts` — `applyWind`/`crossedCards`, shared by the grass, shrubs and reeds. Both fields drive their uniforms off the same `clock.elapsedTime`, so a gust crosses all of them together; two clocks drift apart within seconds and it reads as a bug immediately.
- `Plaques.tsx` — the exhibit placards, standing a fixed setback outside the **kerb** (not a fixed distance from the centerline, so every placard keeps the same visible gap to the stone even where the ribbon breathes wider) and facing across the trail, so a visitor reads the name before looking up at the tree. Posts, plates and health dots are three InstancedMeshes covering the whole forest; only the *text* is per-tree, distance-gated with hysteresis. They are sized against the undergrowth rather than at a realistic placard scale, because at that scale they vanish into the grass.
- `CameraRig.tsx` — the selection fly-in and the guard rails, together because they are one state machine: selection owns the camera until it arrives or the user grabs the controls, then a late-priority frame callback clamps the target inside the exhibit and keeps the eye above the terrain. There is deliberately **no opening move** — a three-second drift from a wide shot down to the trail head meant the first thing a visitor met was an animation to wait out; the view now starts where that move used to end.

**Geometry caching for scale**: `SpeciesBuild`s are cached per `(species, variant, foliageDensity)` in a module-level `Map` in `trees/registry.ts`, never per tree — geometry is a pure function of those three, so a hundred trees sharing a variant reuse one build. Don't key the cache on `tree.id`.

**Seeded determinism is load-bearing, not style**: every source of visual variation (branch curvature, foliage jitter, which variant a tree gets, layout position, prop and filler-tree placement) must derive from `seededRandom(seed)` (a string-seeded PRNG in `utils.ts`) keyed on something stable like `tree.id` or a fixed string literal — never `Math.random()`. This is what keeps SSR and client renders identical; a live hydration mismatch was hit once from this exact class of bug.

**Reduced motion**: `hooks/usePrefersReducedMotion.ts` reads `(prefers-reduced-motion: reduce)` via `useSyncExternalStore` (same pattern as `DarkModeContext`/`LanguageContext` below, not `useState`+effect) and gates every continuous animation — wind, hover easing, mote drift, mist scroll, the camera's opening move, and the day↔night transition (which snaps to the target theme instead of easing). The foliage LOD crossfade is deliberately *not* gated: it is a level-of-detail transition, not decoration, and snapping it would read as the canopy popping. Server snapshot is `false` — safe because the value only feeds `useFrame` callbacks and ref writes, never JSX branches.

**Quality tiers**: `hooks/useQualityTier.ts` detects device capability via `navigator.hardwareConcurrency`, `navigator.deviceMemory`, `prefers-reduced-data`, and `pointer: coarse` (no GPU fingerprinting — `WEBGL_debug_renderer_info` is deliberately not used for privacy). Returns `"low"`/`"mid"`/`"high"`/`"ultra"`. The single biggest lever is `detailedLeaves`: false collapses the foliage LOD permanently to the cheap canopy hull, which is the largest fill-rate saving available and the first thing to go on weak hardware. `waterDetail` is the next one down — it drops the lily pads and the stream mist, both pure fill rate. Server snapshot is `"mid"`. The hook only affects R3F post-processing params and instance counts, not JSX branches, so no hydration risk.

**Verifying visual changes**: in development `Forest3D` exposes `window.__forestState` (the R3F root state) and `window.__forestControls` (the OrbitControls *ref*, since the controls arrive a frame after mount). Together they let tooling drive the camera and measure the frame budget — `gl.info.render.calls`/`.triangles` with `autoReset` off over a fixed number of frames is how the triangle count was brought down 3x. Screenshots must come from headless Chrome with SwiftShader over a real wait; the preview tool's hidden tab freezes rAF and never renders a frame.

### Theming — must match `mertsoylu.dev`

This page ships on a subdomain of the owner's main portfolio (a separate Vite/React repo, not in this workspace) and is styled to feel like the same site, not a separate tool: same warm sand/clay CSS-variable palette (`--canvas`/`--surface`/`--fg`/`--muted`/`--accent`/…, light + `.dark` in `globals.css`), same Fraunces (display) + Inter (body) font pairing, same dark-default-with-toggle and TR/EN-toggle behavior — but with its **own** localStorage keys (`cv-orman-dark-mode`, `cv-orman-language`), independent of the main site's state.

`DarkModeContext`/`LanguageContext` read their persisted value via `useSyncExternalStore`, not `useState` + a `useEffect` that calls `setState` — the latter trips the `react-hooks/set-state-in-effect` lint rule and is the wrong tool for "synchronize with an external store" per React's own guidance. Both contexts' server snapshot is a fixed default (`true` / `"tr"`) matching the pre-hydration script in `app/layout.tsx`'s `<head>`, so server and first client render always agree — don't reintroduce a lazy `useState(() => localStorage...)` initializer, it reintroduces the hydration-mismatch risk this pattern was written to avoid.

Copy strings live in `lib/i18n/dict.ts` (`useT()` hook) — tr/en only, no i18n library.

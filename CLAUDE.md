# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## This is NOT the Next.js / React you know

This repo runs **Next.js 16 (Turbopack) + React 19** — recent enough that APIs, conventions, and file structure may differ from training data. Before writing Next-specific code (route segment config, caching/`revalidate`, server vs client component rules, `app/` conventions), read the relevant guide in `node_modules/next/dist/docs/` and heed deprecation notices rather than assuming older-Next behavior.

## What this is

`cv-orman` is a standalone Next.js page (deployed to a subdomain of mertsoylu.dev) that renders the owner's own GitHub repos as trees in a 3D forest. Tree size comes from stars/commits/age, tree color/wilt comes from days-since-last-push, tree species comes from primary language. It's a single-user, single-page app — no auth, no multi-tenancy, no database.

## Commands

```bash
npm run dev      # Turbopack dev server, http://localhost:3000
npm run build    # production build (also runs the TypeScript check)
npm run start    # serve the production build
npm run lint     # eslint (flat config: eslint-config-next core-web-vitals + typescript)
npx tsc --noEmit # typecheck only, faster than a full build
```

There is no test runner configured in this repo. Verification is tsc + lint + build, plus manually checking `/` in a browser (this is a visual/3D app — type-checking does not catch rendering or hydration bugs).

Required env vars (see `.env.example`): `GITHUB_TOKEN` (a GitHub PAT with `public_repo` scope — despite the `.env.example` comment, a fine-grained `github_pat_...` token has been confirmed to work fine against the GraphQL endpoint, not just classic tokens) and `GITHUB_USERNAME`. Without both, `/` and `/api/repos` return a 502 with an explanatory message instead of failing silently.

## Architecture

### Data pipeline (no database, stateless)

Growth/health are recomputed from live GitHub data on every fetch, cached only via Next's ISR (`revalidate`) — there is deliberately no DB, because GitHub's API already exposes everything needed to derive current state.

```
lib/github/query.ts        GraphQL query string (single query, paginated via `after`)
  -> lib/github/client.ts  fetchAllRepoNodes(): pages through all repos, throws GitHubFetchError
  -> lib/github/normalize.ts  normalizeRepoNodes(): drops archived repos (no GraphQL arg for that —
                               isFork is filtered server-side, isArchived must be filtered here),
                               delegates scoring to lib/forest/growth.ts (computeGrowthScore),
                               lib/forest/health.ts (computeHealthStage), and lib/forest/species.ts
                               (mapLanguageToSpecies, a plain language->species lookup table)
  -> lib/forest/layout.ts  computeForestLayout(): gallery-path placement -> {x, y} per tree id
  -> PlacedTreeData[]      passed straight into the renderer
```

`src/lib/forest/treeData.ts` (`TreeData` / `PlacedTreeData`) is the contract between the data layer and the renderer. Renderers only ever read the precomputed `growthScore` (0-1, drives scale) and `healthStage` (0-1, drives color/wilt) — never raw `stars`/`commitCount`/`lastPushedAt` directly. Keep that separation: it's what let three renderer prototypes (2D SVG, 3D, 2.5D parallax) get built and compared against the same data before 3D was picked and the other two deleted.

`app/page.tsx` is a Server Component that calls `fetchAllRepoNodes` → `normalizeRepoNodes` → `computeForestLayout` **directly**, not by fetching its own `/api/repos` route, then hands the resulting `PlacedTreeData[]` (plus any fetch error) to `components/ForestPageClient.tsx` — a Client Component that owns the hero/legend overlay, stats, error/empty states, tree-selection state, and mounts `Forest3D` + `TreeDetailPanel`. `/api/repos` still exists as a standalone JSON endpoint but is not on the real page's request path. Both `route.ts` and `page.tsx` declare `export const revalidate = 3600` as a hardcoded literal — Next.js requires route segment config to be statically analyzable, so it can't just import `REVALIDATE_SECONDS` from `lib/config.ts`; keep these three in sync by hand if you change the cache duration.

`ForestPageClient.tsx` also renders a visually-hidden (`.sr-only`) `RepoFallbackList` alongside the canvas — the 3D scene has no DOM equivalent, so this is the only path screen readers, crawlers, and no-JS/no-WebGL clients have to the repo data. `Forest3D` is wrapped in an `ErrorBoundary` (class component; function components can't catch render errors) whose fallback re-renders `RepoFallbackList` visibly with a short explanatory heading — for when WebGL context creation itself throws. A `sceneReady` flag (flipped by `Forest3D`'s `onReady` prop, fired from the `Canvas`'s existing `onCreated`) gates a `SceneLoadingIndicator` overlay so there's no blank gap between the route's `loading.tsx` (server fetch) and the scene's first WebGL frame (client init) — `loading.tsx` renders the same `SceneLoadingIndicator` component so the two waits read as one continuous state.

`lib/config.ts` centralizes the tunable weights: `GROWTH` (stars/commits/age weighting + soft caps), `HEALTH` (healthy/wilted day thresholds + wilted floor), `LAYOUT` (gallery-path row spacing, lateral offset base/growth/jitter). `GITHUB_USERNAME`/`GITHUB_TOKEN` are read via lazy getters (`getGithubUsername()`/`getGithubToken()`), not top-level constants — `next build` imports route modules to collect segment config without ever calling the handlers, so an eager `requireEnv()` at module scope breaks the build whenever secrets aren't present at build time.

`computeForestLayout()` lines trees up along a straight exhibit path centered on plane `(0,0)` — sorted-id order, alternating left/right in pairs, sideways offset scaled by `growthScore` plus a seeded jitter — rather than scattering them across a fixed-size plane. There is no `PLANE_WIDTH`/`PLANE_HEIGHT` bound; the path is exactly as long as it needs to be for however many repos exist, and the renderer derives ground/path/camera sizing from the actual tree spread instead of a hardcoded plane size.

### Renderer: `components/renderers/three-3d/`

react-three-fiber + drei. This is the only renderer — 2D SVG and 2.5D parallax prototypes existed during the style-comparison phase and were deleted once 3D was chosen; don't resurrect them from git history without checking with the user first.

- `Forest3D.tsx` — scene root: camera, `OrbitControls`, ground + gravel path plane, one `ExhibitEnvironment`, one `TrunkInstanceGroup` per `(species, variantIndex)` bucket, one `Tree3D` + `Signpost` per tree. Ground size, path length, camera distance and `OrbitControls` min/max distance are all computed from the tree set's actual bounding box (`useMemo` over `positions`), not fixed constants — the exhibit self-sizes to repo count. `planeToWorld` no longer subtracts a half-plane-size centering offset, since `computeForestLayout` already centers the path on `(0,0)`. A signpost sits at `tree.z + SIGNPOST_FORWARD_OFFSET` (toward the camera, not at the trunk's own depth) so a wide canopy can never render in front of its own plaque. Sky/fog/all three scene lights + the sun/moon are delegated to `CelestialSystem` (see below), passed `isDark` (wired to `useDarkMode()` in the caller) plus `cameraDistance` (the celestial radius scales off it). A `hoveredIdRef` (`useRef<string|null>`, not state — read every frame, doesn't need re-renders) is the single source of truth for "which tree is hovered," shared by every `Tree3D` and `TrunkInstanceGroup` so bark and foliage pop in sync regardless of which one the pointer actually landed on.
- `CelestialSystem.tsx` — owns the whole sky: the drei `<Sky>` dome, scene `<fog>`, the three scene lights (ambient/hemisphere/directional key), and a visible sun + moon. Holds both `NIGHT_PRESET`/`DAY_PRESET` (`LightingPreset` objects — warm dusk vs clear midday; these moved here out of `Forest3D`). The theme change is **animated, not a snap**: a single `useFrame` eases a `dayFactor` (1 = day, 0 = night) toward `isDark` via `THREE.MathUtils.damp`, then imperatively lerps *every* value off it each frame — Sky shader uniforms (`turbidity`/`rayleigh`/`mie*`/`sunPosition`, reached through the `<Sky ref>`'s `.material.uniforms`), `scene.fog.color`, and each light's color/intensity/position — so flipping the site toggle drives real, continuous lighting (sun sets, moon rises, key light warms + dims). The JSX props on `<Sky>`/lights/`<fog>` are **mount-time seeds only**: `useFrame` runs before every painted frame and overwrites them, which is what prevents a snap on toggle — don't move any of these values back to being driven by React props. Sun rides `dayFactor`, moon rides `1 - dayFactor`, on opposite azimuths, each placed on an arc (`placeBody`) and faded via `smoothstep` as it dips below the horizon (`fadeBody` scales a baked `userData.baseOpacity` per child material). Sun/moon are unlit `meshBasicMaterial` with `fog={false}` + `toneMapped={false}` so they always read as bright discs, never shaded balls or fogged smudges — and `fog={false}` is why their large radius can ignore `fogFar`. `PHI_MAX` is deliberately low (~29°): the camera rests near-horizontal (55° FOV), so a zenith-high body would sit above the frustum; keeping the radius a multiple of `cameraDistance` (both grow with repo count) holds the apparent elevation constant so they stay framed at rest. Snaps instantly (no ease) under `usePrefersReducedMotion`.
- `speciesRegistry.ts` — the `SPECIES_BUILDERS` map, the `(species, variantIndex)` → `SpeciesBuild` cache (`getSpeciesBuild`), and the seeded per-tree derivations (`getVariantIndex`, `getTreeJitter`, `getTreeSway`) that used to live in `Tree3D.tsx`. Pulled out so `Tree3D` (foliage/litter) and `TrunkInstanceGroup` (trunk/branch) compute identical rotation/scale/sway for a given tree from the same source instead of two copies drifting apart.
- `TrunkInstanceGroup.tsx` — renders every tree's trunk/branch parts for one `(species, variantIndex)` bucket as a shared set of `THREE.InstancedMesh` (one per part index, raw Three.js, not drei's `<Instances>`, since per-frame `setMatrixAt` needs direct imperative control), instead of `Tree3D`'s old `treeCount * partsPerTree` individual `<mesh>` draw calls per bucket. Valid because `part.color` never varies per tree within a variant (species builders bake one bark color per build) — a shared material per part is exact, not an approximation. Per-instance transform is composed by hand each frame (`baseMatrix * hoverScale * sway * partLocal`, scratch `THREE.Matrix4`/`Euler` objects reused across the loop, never allocated per-instance) since sway and hover both animate continuously. Sets `frustumCulled={false}` on every instanced mesh, same reasoning as `ExhibitEnvironment`'s backdrop ring: instance matrices set via `setMatrixAt` don't feed into the mesh's default bounding volume, so culling would use a stale bounds and risk popping the whole group out of view. **Trade-off**: standard `MeshStandardMaterial` has no per-instance emissive, so the hover glow `Tree3D` puts on foliage doesn't extend to bark — hovering still pops the whole tree's scale (trunk and foliage read the same `hoveredIdRef`/jitter/sway), it just doesn't add a glow on top for the bark specifically.
- `Tree3D.tsx` — one tree's instanced foliage cluster + fallen-leaf litter only (trunk/branch moved to `TrunkInstanceGroup`, see above). Applies `growthScore` as a pure scale multiplier and `healthStage` as a foliage-color lerp toward a shared dry/wilted palette. Hover is damped, not toggled: a `hoverT` ref eases toward 0/1 via `THREE.MathUtils.damp` inside `useFrame`, reading the shared `hoveredIdRef` as its target (snaps instantly instead under `usePrefersReducedMotion`) — driving both the canopy's scale-up and an emissive-intensity ramp on a ref to the foliage material. There's no direct `hovered ? x : y` prop on scale/material, and no local `hovered` state at all anymore — don't reintroduce either.
- `Signpost.tsx` — museum-placard: a wooden post + a `Billboard`-wrapped plaque (`drei` `Text`) showing `tree.name` plus a small health-colored dot, positioned between the path center and the tree so it reads before the tree itself; shares the same `onClick` → `onSelect(tree.id)` wiring as the tree. The plaque group is LOD-gated (`LOD_NEAR`/`LOD_FAR` world-unit thresholds with hysteresis between them, checked against camera distance every frame) so it's only visible on hover or up close — a permanent `Text` mesh per tree reads as a wall of overlapping plaques once repo count climbs past a few dozen. The post itself stays always-visible so the tree keeps a clickable/wayfinding anchor at any distance.
- `ExhibitEnvironment.tsx` — everything in the garden that isn't a tree or its placard: grass tufts, rocks, shrubs, path-edge pebbles, bollard lamps, benches, a distant tree-line + hill silhouette ring (an ellipse matching the ground's aspect, not a circle) that gives the horizon something other than bare sky, and fireflies (gated behind a `showFireflies` prop wired to `isDark` — a night-garden detail, skipped entirely under the day preset). The ring's cones/domes sit on a second, oversized terrain plane that `Forest3D.tsx` renders below the real ground (`y = -0.15`) — without it, backdrop props have no surface to root into and read as floating discs. **The backdrop ring's distance from camera must stay inside `fogFar`** (`Forest3D.tsx`'s `fogFar: Math.max(110, distance * 2.8)`): the ring sits at `groundSize/2 + ~15-40`, so for small tree counts (short `groundSize`, short camera `distance`) a `fogFar` tied only to `distance` undershoots the ring's real distance and every backdrop instance renders as one flat, fully-fogged solid color regardless of its own material color. If you change `GROUND_MARGIN`, camera distance, or the ring's placement offsets, re-check this relationship. Fireflies' per-frame drift runs entirely in the vertex shader (spliced into the stock `PointsMaterial` shader via `onBeforeCompile` at `#include <begin_vertex>`, driven by `uTime`/`uMotion` uniforms) rather than a 110-point CPU loop mutating a `BufferAttribute` every frame — `uMotion` is zeroed under `usePrefersReducedMotion` instead of skipping a frame callback.
- `species/organicBuilder.ts` — shared geometry primitives: `buildLimb` (a curved, tapered, bark-noised chain of cylinder segments following a CatmullRom spine), `buildBranchSystem` (forks primary branches + secondary twigs off a limb), `buildRootFlare` (buttress roots fanning outward-down from the trunk base, built from `buildLimb` with no bark noise), `scatterFoliageClumps` (jittered instanced foliage positions around branch tips).
- `species/{oak,pine,sakura,palm,birch,generic}.ts` — one `buildX(rand)` function per species, composed from the primitives above, each returning a `SpeciesBuild` (trunk/branch mesh parts + a shared foliage clump geometry + clump transforms). Every species must stay visually distinguishable by silhouette alone (branch spread angle, foliage density, trunk taper), independent of color. `generic.ts` is the only one without a root flare or branch system — it's the fallback for repos with no mapped language.

**Geometry caching for scale**: `SpeciesBuild`s are cached per `(species, variantIndex)` in a module-level `Map` in `speciesRegistry.ts`, not per tree — geometry is a pure function of the seeded variant, so 100+ trees sharing a variant reuse one build instead of rebuilding. Don't key the cache on `tree.id`. Trunk/branch parts additionally get batched *across* every tree in a bucket by `TrunkInstanceGroup` (see above) — the geometry cache alone stops rebuilding, but without that batching each tree still emitted its own draw call per part.

**Seeded determinism is load-bearing, not style**: every source of visual variation (branch curvature, foliage jitter, which variant a tree gets, layout position, garden-prop placement in `ExhibitEnvironment.tsx`) must derive from `seededRandom(seed)` (a string-seeded PRNG in `utils.ts`) keyed on something stable like `tree.id` or a fixed string literal — never `Math.random()`. This is what keeps SSR and client renders identical; a live hydration mismatch was hit once from this exact class of bug.

**Reduced motion**: `hooks/usePrefersReducedMotion.ts` reads `(prefers-reduced-motion: reduce)` via `useSyncExternalStore` (same pattern as `DarkModeContext`/`LanguageContext` below, not `useState`+effect) and gates every continuous animation — tree sway, hover easing, `ExhibitEnvironment`'s firefly drift, and `CelestialSystem`'s day↔night lighting/sun/moon transition (snaps to the target theme instead of easing). Server snapshot is `false` — safe because the hook's value only feeds `useFrame` callbacks and ref writes, never JSX branches, so there's no visible SSR/client markup divergence (Client Components do SSR-render their container JSX, but the reduced-motion value doesn't change what JSX is emitted).

**Quality tiers**: `hooks/useQualityTier.ts` detects device capability via `navigator.hardwareConcurrency`, `navigator.deviceMemory`, `prefers-reduced-data`, and `pointer: coarse` (no GPU fingerprinting — `WEBGL_debug_renderer_info` is deliberately not used for privacy). Returns `"low"`/`"mid"`/`"high"`, with `QUALITY_PRESETS` driving `Forest3D`'s `multisampling`/`bloom`/`n8ao`/`dpr`, `CelestialSystem`'s `shadowMapSize` (1024 low/mid, 2048 high), and `ExhibitEnvironment`'s grass density/firefly count/lamp+bench count. Server snapshot is `"mid"`. The hook only affects R3F post-processing params and prop counts, not JSX branches, so no hydration risk.

### Theming — must match `mertsoylu.dev`

This page ships on a subdomain of the owner's main portfolio (a separate Vite/React repo, not in this workspace) and is styled to feel like the same site, not a separate tool: same warm sand/clay CSS-variable palette (`--canvas`/`--surface`/`--fg`/`--muted`/`--accent`/…, light + `.dark` in `globals.css`), same Fraunces (display) + Inter (body) font pairing, same dark-default-with-toggle and TR/EN-toggle behavior — but with its **own** localStorage keys (`cv-orman-dark-mode`, `cv-orman-language`), independent of the main site's state.

`DarkModeContext`/`LanguageContext` read their persisted value via `useSyncExternalStore`, not `useState` + a `useEffect` that calls `setState` — the latter trips the `react-hooks/set-state-in-effect` lint rule and is the wrong tool for "synchronize with an external store" per React's own guidance. Both contexts' server snapshot is a fixed default (`true` / `"tr"`) matching the pre-hydration script in `app/layout.tsx`'s `<head>`, so server and first client render always agree — don't reintroduce a lazy `useState(() => localStorage...)` initializer, it reintroduces the hydration-mismatch risk this pattern was written to avoid.

Copy strings live in `lib/i18n/dict.ts` (`useT()` hook) — tr/en only, no i18n library.
